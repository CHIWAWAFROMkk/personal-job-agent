# Epic 4：通知登记、日程与求职看板

## 使用方式

1. 打开“进度”，点击“登记通知”，粘贴收到的招聘邮件或短信正文。
2. 点击本地识别，核对公司、状态、日期、时间与链接，选择对应的已有岗位。识别公司不等于自动匹配岗位；必须本人选择。
3. 需要保存日程时，确认它是测评截止还是面试开始，并填写完整时间。界面时间使用上海时间（UTC+08:00），不是浏览器所在地区的时区。
4. 勾选核对确认，再登记。不能确定时间时可只登记状态，不创建日程；不要把没有时分的日期擅自当作当天午夜。
5. 在进度页查看五列看板、48 小时内待办与全部日程。岗位卡片可打开详情；日程“标记完成”仅完成该提醒，不把测评当作通过，也不修改岗位状态。
6. “导出日历”下载当前未完成日程的 `.ics` 文件，由本人导入日历软件。

这不是邮箱或短信后台监控器：只处理本人主动粘贴的通知。不会自动读取收件箱、执行招聘链接或替用户参加测评。

## 解析边界与隐私

- `tracking_parser.py` 使用本地规则，不调用模型、网络服务或 DNS 查询；通信正文不写入 SQLite、文件或日志，也不会因本次解析发送给云端。
- 解析结果只是待确认建议。ATS 平台名称（例如北森、Moka）不自动当成雇主；多个状态、多个时间、缺少时间、取消和假设性表述等会保守处理，并显示人工核对提示。
- 相对日期及缺少年份的时间可能依赖本次解析日期，因此必须核对警告。其他时区或无法确认的时间由本人转换；系统不声称理解所有招聘通知格式。
- 链接仅做语法安全检查：允许公共 HTTP(S) 地址，拒绝脚本协议、凭据、本地地址、异常端口等。不会访问链接核实真伪、招聘时效或安全性。打开前仍需本人检查。
- 登记后保存的是已确认的岗位状态、日程及链接。链接可能包含个人邀请参数，日历也包含岗位信息，均应当作私人材料保管，勿公开分享。

## 数据一致性

`JobRepository.apply_tracking_update()` 在同一个 SQLite `BEGIN IMMEDIATE` 事务内完成：岗位状态、application 当前状态、状态历史事件、日程以及幂等请求记录。任一步失败会回滚；状态相同不重复生成状态变更事件。

外部识别状态映射：

| 通知状态 | 现有数据库状态 |
| --- | --- |
| `oa_pending` | `assessment` |
| `interview_scheduled` | `interview_1` |
| `rejected` | `rejected` |
| `offered` | `offer` |

现有规范状态也可使用，包括 `written_test`、`interview_2`、`final_interview`。继续沿用原有禁止静默回退的状态规则。

- `request_id` 在同一次内容的重试中保持不变；相同键、相同内容返回重复成功，不重复写入。相同键用于不同内容会拒绝。
- 相同岗位、类型和时间的日程唯一；不同时间的日程保留，不猜测新邀请是否替代旧邀请。需要清除旧提醒时由本人标记完成。
- 看板优先采用 application 状态，避免旧岗位字段覆盖真实流转。已归档岗位以及拒绝、撤回、Offer 等已结束岗位的提醒不出现在待办和导出日历中。
- 本次只增补表结构，不替换已有数据库或用户档案。

## HTTP 接口

全部接口沿用本地操作授权 `X-Job-Agent-Token`，包括看板和日历读取；请求来源与 Host 也由现有授权逻辑检查。不要把令牌放到可分享的 URL 中。

| 接口 | 请求 / 响应 |
| --- | --- |
| `POST /api/tracking/parse-message` | `{text}`，最多 20000 字符；返回 `company,status,event,links,warnings,evidence`。没有确定信息时字段可为 `null`。 |
| `POST /api/tracking/apply-update` | `{confirmed:true,job_id,status,request_id,event?}`；返回 `{ok,duplicate,changed,reminder_id}`。 |
| `GET /api/tracking/board` | `{jobs,reminders}`；岗位包括 `job_id,company,title,status`；提醒包括 `id,job_id,company,title,kind,at,url,completed,created_at`。 |
| `POST /api/tracking/reminders/{id}/complete` | `{confirmed:true}`；返回 `{ok:true}`。 |
| `GET /api/tracking/calendar.ics` | 返回带下载文件名的 `text/calendar`。前端使用已授权请求下载，不暴露无鉴权日历订阅链接。 |

`event` 格式为 `{kind:"oa"|"interview",at:"2026-09-25T18:00:00+08:00",url?:"https://exam.example/test"}`。时间必须包含时区；类型必须与状态相符。省略 `event` 即只更新状态。

日历使用 RFC 5545 格式，包含稳定 UID、DTSTAMP、UTC DTSTART、URL、中文文本转义及 75 字节 UTF-8 行折叠。测评 DTSTART 表示截止时点，面试表示开始时点；不虚构持续时长。

**日历是导出时的快照，不是实时订阅或推送。** 后续改动需要重新导出并核对日历软件中的旧事项。应用内倒计时不等同于操作系统通知，关闭应用后不会由本模块持续发出提醒。

## 界面与验收

- 继承现有 Aurora / Cosmic 主题令牌、透明状态胶囊和玻璃抽屉，不引入独立主题系统。
- 看板宽屏五列，宽度不超过 1100px 时三列，不超过 650px 时单列。
- 右侧登记抽屉最大 560px，关闭区保持可见；窄屏自适应。核心操作提供至少 44px 触控目标、可见焦点、语义提示以及降低动态/透明度支持。这些措施不代表整个软件已经通过 WCAG AAA 审计。
- `tests/test_tracking_parser.py`：合成通知、格式歧义、时间与链接边界。
- `tests/test_tracking_repository.py`：事务回滚、幂等冲突、日程保留、权威状态及日历转义。
- `tests/test_tracking_api.py`：真实本地 HTTP 授权、解析到登记、完成及导出流程。
- UI 验收由本项目 Playwright 脚本使用合成数据执行。具体通过数量以本次实际测试输出为准；样例测试通过不等于所有真实招聘短信或网站格式覆盖率 100%。

2026-09-20 本次验证记录：全量 Python 测试 354 项通过；随后新增解析边界测试后，相关定向测试 73 项通过（未将这两个数字相加声称新的全量结果）。Node 测试 21 项通过；三个窗口尺寸的界面验收覆盖登记、完成日程与刷新后状态保留。未改动真实私人求职数据。

新增源码不等于旧桌面安装包已经升级；发布 EXE 前仍需完成桌面打包与安装运行验证。
